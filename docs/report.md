Задание 0.1. Принципы информационной безопасности

Конфиденциальность. Информацию могут просматривать только пользователи с соответствующими правами. Для этого применяются вход по логину и паролю, проверка доступа и защита передаваемых данных. Пользователь приложения должен видеть только доступные ему устройства. Получение показаний чужого устройства без разрешения будет нарушением конфиденциальности. Пароли и секретные токены также не должны выводиться на странице или попадать в открытые журналы.

Целостность. Данные должны сохранять корректность и быть защищены от случайного или неправомерного изменения и удаления. Для этого используются ограничения допустимых значений, связи между таблицами и проверка вводимых данных. Например, состояние реле принимает только значения 0 и 1, а показания должны относиться к существующему устройству. Запись неверного значения или изменение чужой команды нарушает целостность. Связанные изменения сохраняются одной транзакцией, чтобы команда и запись о ней не расходились.

Доступность. Пользователь с необходимыми правами должен получать информацию и пользоваться приложением, когда это требуется. Доступность зависит от работы сервера, сети и возможности восстановить данные после сбоя. Слишком частые запросы одного устройства не должны мешать остальным пользователям. При этом ограничения должны учитывать обычную нагрузку: слишком строгая блокировка может препятствовать нормальной работе. Резервные копии помогают восстановить сведения при их утрате.

Задание 0.2. Меры защиты базы данных

Ролевая модель доступа RBAC. Роль определяет, какие операции доступны пользователю. В приложении наблюдатель может просматривать показания и историю, а оператор также может управлять реле. Разрешения проверяются на сервере при каждом действии. В браузере недоступные кнопки скрываются, но отправленная вручную команда всё равно должна пройти проверку прав.

Хеширование паролей. В базе данных хранится хеш пароля со случайной солью. Для его создания используется password_hash, а при входе введённый пароль проверяется через password_verify. Исходный пароль в базе не сохраняется. Передавать его следует по HTTPS, без включения в адрес страницы и без сохранения в открытом хранилище браузера.

Подготовленные запросы. Сервер передаёт SQL-текст и значения отдельно через prepare и execute. Поэтому введённая строка обрабатывается как данные и не меняет структуру запроса. Проверки в браузере помогают правильно заполнить форму, а на сервере повторно проверяются типы и допустимые значения. Имена таблиц и столбцов выбираются из заранее определённого списка.

Представления VIEW. Представление задаёт состав полей, которые можно получить из нескольких таблиц. В v_device_dashboard объединены сведения об устройстве, его состоянии и доступе пользователя. Хеши паролей и токенов в него не включены. Сервер дополнительно отбирает строки по пользователю, чтобы браузер получал только разрешённые данные.

Ограничения целостности. Первичный ключ определяет запись, UNIQUE запрещает повторяющиеся значения, внешний ключ проверяет связи между таблицами. NOT NULL требует заполнить поле, CHECK ограничивает допустимые значения. Сервер проверяет данные до записи в БД. Ограничения формы в браузере служат дополнительной проверкой и могут быть обойдены пользователем.

Шифрование, анонимизация и маскирование. Шифрование защищает данные с помощью ключа и позволяет восстановить исходное значение. Его применяют к передаче данных и резервным копиям. Анонимизация используется для подготовки данных, по которым нельзя определить человека с учётом доступной дополнительной информации. Маскирование скрывает часть значения при выводе, например часть номера телефона, сохраняя исходную запись в БД. В браузер не следует передавать сведения, на просмотр которых у пользователя нет прав.

Обработка ошибок. Сервер возвращает понятное сообщение без SQL-текста, паролей и внутренних путей. Сведения для поиска причины сохраняются в закрытом журнале. Пользователь должен понимать, нужно ли исправить введённые данные или повторить действие позже. При выводе сообщения в HTML специальные символы экранируются.

Журналирование событий. На сервере фиксируются пользователь или устройство, действие, время и результат. Это позволяет просмотреть историю и установить причину ошибочных операций. Пароли и токены в журнал не записываются. В браузере история доступна только пользователю с правами на соответствующее устройство.

Сетевая изоляция. Браузер и устройство обращаются к веб-приложению, а подключение к БД выполняет сервер. Доступ к порту СУБД ограничивают разрешёнными адресами. Клиенты не получают пароль служебной учётной записи БД. Файлы конфигурации и сессий размещаются вне каталога, открытого через веб-сервер.

Резервное копирование. Копии данных и структуры БД позволяют восстановить работу после сбоя или удаления записей. Их создают регулярно, защищают от постороннего доступа и хранят отдельно от основной базы. Возможность восстановления проверяют на другой БД. Пользовательский экспорт должен содержать только разрешённые сведения; он не заменяет полную серверную копию.

Задание 1.1. Приложение для управления устройством

Приложение разработано на PHP для работы с MySQL по урокам 1-4 LAZY SMART. Оно позволяет просматривать температуру и управлять реле через веб-страницу. Реле работает как управляемый выключатель подключённого оборудования. Для демонстрации обмена данными используется программный симулятор устройства.

Пользователь сохраняет команду включения или выключения на сервере. Устройство передаёт температуру и фактическое состояние реле, затем получает команду COMMAND 0 EOC или COMMAND 1 EOC. Если команда ещё не задана, сервер возвращает COMMAND ? EOC. Например, Term=216 соответствует температуре 21,6 °C.

В исходном примере выбирается одно устройство через $id = 1. В следующих заданиях добавлена работа с несколькими устройствами. Команда и фактическое состояние реле хранятся отдельно: показания обновляются после получения новых данных от устройства.

Задание 1.4. Идентификация устройства

Для идентификации устройства используются уникальный внешний код UID и секретный токен. Код позволяет найти устройство, а токен подтверждает право передавать данные от его имени. Внутренний числовой ключ сохраняется в БД для связи таблиц.

```
$uid = bin2hex(random_bytes(16));
$token = bin2hex(random_bytes(32));
$tokenHash = hash('sha256', $token);
```

В базе хранится хеш токена. Сервер сравнивает его с хешем полученного значения и принимает показания только при совпадении. Одного знания UID для изменения данных недостаточно.

Задание 1.5. Учёт действий и история управления

Добавлена таблица user_events. В ней сохраняются пользователь, устройство, действие, запрошенная команда, время и результат. Ссылка «История управления» в карточке открывает страницу событий выбранного устройства. Доступ к истории проверяется на сервере.

```
SELECT e.happened_at, u.username, e.action, e.command, e.outcome
FROM user_events e
JOIN users u ON u.id=e.user_id
WHERE e.device_id=?
ORDER BY e.id DESC
LIMIT 100;
```

События выводятся от новых к старым. В истории видны просмотры и запросы управления, включая отклонённые обращения. Принятие команды сервером не подтверждает переключение физического реле: новое состояние должно сообщить устройство.

Задание 1.6. Блокировка пользователя

Для проверки установлен порог: 10 обращений к одному устройству за период 60 секунд. На 11-м обращении доступ блокируется на 60 секунд. Учитываются просмотр карточки, история и команды. Порог выбран для демонстрации, поскольку в условии он не указан.

Триггер bi_user_events обновляет счётчик в device_access и записывает результат события. Во время блокировки состояние устройства и кнопки управления не выводятся. Остальные устройства пользователя доступны.

Листинг 1. Триггер блокировки пользователя

```
DELIMITER $$
CREATE TRIGGER bi_user_events BEFORE INSERT ON user_events
FOR EACH ROW
BEGIN
    DECLARE t DATETIME(6);
    DECLARE w DATETIME(6);
    DECLARE b DATETIME(6);
    DECLARE db DATETIME(6);
    DECLARE n INT UNSIGNED;
    DECLARE r VARCHAR(16);
    SET t = UTC_TIMESTAMP(6);
    SET NEW.happened_at = t;
    -- Единый порядок блокировок: сначала устройство, затем доступ.
    SELECT blocked_until INTO db FROM devices
      WHERE id = NEW.device_id FOR UPDATE;
    SELECT window_start, request_count, blocked_until, role INTO w,n,b,r
      FROM device_access
      WHERE user_id = NEW.user_id AND device_id = NEW.device_id FOR UPDATE;
    IF NEW.action = 'control' AND r <> 'operator' THEN
        SET NEW.outcome = 'forbidden';
    ELSEIF b IS NOT NULL AND b > t THEN
        SET NEW.outcome = 'user_blocked';
    ELSE
        IF w IS NULL OR t >= w + INTERVAL 60 SECOND THEN
            SET w = t;
            SET n = 0;
        END IF;
        SET n = n + 1;
        SET b = NULL;
        SET NEW.outcome = 'allowed';
        IF n > 10 THEN
            SET b = t + INTERVAL 60 SECOND;
            SET NEW.outcome = 'user_blocked';
        ELSEIF db IS NOT NULL AND db > t THEN
            SET NEW.outcome = 'device_blocked';
        END IF;
        UPDATE device_access SET window_start=w, request_count=n, blocked_until=b
          WHERE user_id=NEW.user_id AND device_id=NEW.device_id;
    END IF;
END$$
DELIMITER ;
```

Прямой запрос к странице управления также отклоняется. Повторные обращения во время блокировки не продлевают её срок.

Задание 1.7. Блокировка устройства

Устройству разрешены 30 корректных запросов с действительным токеном за период 60 секунд. На 31-м запросе триггер bi_device_events устанавливает блокировку на 60 секунд. Запрос проверки связи без новых показаний также учитывается.

Листинг 2. Триггер блокировки устройства

```
DELIMITER $$
CREATE TRIGGER bi_device_events BEFORE INSERT ON device_events
FOR EACH ROW
BEGIN
    DECLARE t DATETIME(6);
    DECLARE w DATETIME(6);
    DECLARE b DATETIME(6);
    DECLARE n INT UNSIGNED;
    SET t = UTC_TIMESTAMP(6);
    SET NEW.happened_at = t;
    SELECT window_start, request_count, blocked_until INTO w,n,b
      FROM devices WHERE id=NEW.device_id FOR UPDATE;
    IF b IS NOT NULL AND b > t THEN
        SET NEW.outcome = 'blocked';
    ELSE
        IF w IS NULL OR t >= w + INTERVAL 60 SECOND THEN
            SET w = t;
            SET n = 0;
        END IF;
        SET n = n + 1;
        SET b = NULL;
        SET NEW.outcome = 'allowed';
        IF n > 30 THEN
            SET b = t + INTERVAL 60 SECOND;
            SET NEW.outcome = 'blocked';
        END IF;
        UPDATE devices SET window_start=w, request_count=n, blocked_until=b
          WHERE id=NEW.device_id;
    END IF;
END$$
DELIMITER ;
```

Заблокированные запросы не изменяют показания и время последней связи. Пользователь видит предупреждение о подозрительном поведении устройства. После окончания срока следующий запрос снова разрешается.

Задание 1.8. Проверка SQL-инъекций

Обращения к БД выполняются через подготовленные запросы PDO. Пример передачи строки 1' OR '1'='1 в параметр UID:

```
$stmt = $pdo->prepare('SELECT id FROM devices WHERE uid=?');
$stmt->execute(["1' OR '1'='1"]);
```

Входные значения не включаются в SQL-текст. Перед выполнением операций проверяются формат UID, допустимые команды и права доступа к устройству.
